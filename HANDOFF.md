## 1. Goal

A personal Android app that wraps https://archiveofourown.org (AO3) so I can:

1. Browse AO3 in-app while online, with the site's full search and filter features.
2. Sign in to my AO3 account.
3. Select works and download the entire work to my phone.
4. Read downloaded works offline.
5. Track where I last left off and resume exactly there when reopening.

**Scope:** strictly personal use, installed on my own device by sideloading. Not for the Play Store and not for distribution.

## 2. Key facts and decisions

- **No official AO3 API.** Everything works through the site's normal web pages.
- **No backend.** All logic runs on-device.
- **One request per work.** AO3 offers official download links (EPUB, MOBI, PDF, HTML). The EPUB bundles all chapters, so downloading a 60-chapter work costs one request. **Do not scrape chapter by chapter.**
- **Browsing uses a WebView, not a native search UI.** AO3 itself provides search, filters, tag autocomplete, and bookmarks. Do not reimplement these.
- **Sign-in happens in the WebView.** Its `CookieManager` cookies are reused by the OkHttp client for downloads, and this avoids hand-rolling CSRF login. It also handles bot checks better than raw HTTP.
- **Reading uses an existing EPUB toolkit (Readium).** Do not build an EPUB renderer. Save Readium's position locator in Room on pause/close and restore it on open.
- **Distribution is sideloading only, via adb.** I build a signed release APK and install it over USB. No prebuilt APKs are published (no GitHub Releases, no Obtainium); anyone else builds from source with their own key. *Decided 2026-09-27;* see step 11 and "Open questions".

## 4. Constraints and gotchas

- **Rate limiting:** AO3 returns HTTP 429 with a `Retry-After` header when throttled. Downloads must be sequential with a few seconds' delay between them, and must honor `Retry-After` before retrying. Human-speed browsing in the WebView is not a concern.
- **Adult content interstitial:** add `view_adult=true` when fetching work pages/downloads **[verify behavior]**.
- **Finding the download URL:** parse the EPUB link from the work page rather than constructing it by hand **[verify the current markup]**.
- **Scraping fragility:** AO3 markup can change. Keep all injected JS and CSS selectors (e.g. `li.work` blurbs, where the work ID is in the element id) in **one dedicated file** so breakages are easy to fix.
- **Signing key:** the release keystore must be kept safe and reused. Android only allows updates over an existing install when signed with the same key, and losing it means uninstalling and losing local data.
- **Use a release build for daily use.** Debug builds are slower and signed with a throwaway key.
- **Terms of Service:** review AO3's ToS, keep this personal-use, and do not bulk-crawl.
- **Android sideloading policy:** Google has been rolling out developer-verification requirements. Installing my own builds on my own device is expected to remain supported **[verify current rules]**.
- **WIP updates:** *(Checked 2026-09-24 against a real 22-chapter WIP download.)* AO3 builds EPUBs with Calibre, which names content files by their place in the book (`<Title>_split_000.xhtml` preface, `_001` title page, `_002` onward one per chapter, then the afterword), and every id in the package is a fresh sequential number. Appending chapters leaves earlier file names alone, but removing or inserting an earlier chapter silently renumbers every later file, so a Readium locator's href can resolve "successfully" to the wrong chapter. Step 9 handles this by comparing content hashes, not names. Still **[verify]**: that Calibre regenerates an *unchanged* chapter byte-for-byte on a later download. If it doesn't, the only effect is landing at the chapter's start instead of the exact spot; confirm by re-downloading a real WIP after its next update.

### Phase 3: Polish

9. **WIP updates.** *(Done 2026-09-26.)* Re-download the EPUB to pick up new chapters while keeping the reading position. When a download replaces an existing copy, the downloader reads the old and new reading order (each file's zip path, SHA-256 and first heading) before and after the swap, and `reconcilePosition` decides what the saved position becomes:
   - the chapter is byte-identical at the same path → kept exactly (new chapters appended, or edits to *other* chapters);
   - identical but under a different file name (an earlier chapter was added or removed) → same spot, new href;
   - the chapter's content changed → start of that chapter, found by its heading, with a one-time reader banner;
   - the chapter can't be found → start of the work, with a banner.

   Chosen over text-anchored bookmarks (store the sentence at the top of the page and search for it after an update), which were considered and dropped as a much larger lift: Readium selection plumbing, sentence segmentation, text normalization and duplicate-match handling, for little gain once chapter navigation (step 9a) covers the remaining gaps by hand. The banner is a `notice` column on `reading_progress` (migration 3→4); any normal save replaces the row without it, so it shows once. Verified on the emulator with a real re-download of a real WIP against planted "older" copies: an edited current chapter (→ chapter start, banner) and an inserted earlier chapter (→ exact spot in the renumbered file).
9a. **Chapter navigation and position seeking.** *(Added and done 2026-09-26.)* Built as a bottom bar over the page (so it never re-paginates): a slider stepping through Readium positions (about a page each) with a live "chapter · percent" preview that jumps on release, and a Chapters button opening a bottom sheet scrolled to the current chapter. Shown when a work opens; a tap in the middle of the page toggles it (edge taps still turn pages), and its down arrow or dragging it down closes it. Swipe-up-to-open and a floating corner button were tried and dropped: the swipe was unreliable in practice and the button covered text. Original plan: in the reader, a chapter list from Readium's `publication.tableOfContents` (it will include Preface and Afterword) that jumps with `navigator.go(link)`, and a way to seek to a point in the work. Seek by Readium's `publication.positions()` (fixed ~1,024-character slices) or a percentage rather than rendered page numbers, which shift with font size and rotation. Position numbers are recomputed after an update, which is fine for manual navigation.

11. **Hardening.** *(Done 2026-09-27, in PRs 1–6 below.)* Originally: cookies in encrypted storage, sensible error and offline states, GitHub Releases plus Obtainium for updates. Also picks up notes 1 (cancel a download) and 6 (persist sort and filter) from "Notes to revisit in Phase 3". Scope revised by decision on 2026-09-27:
    - **"Cookies in encrypted storage" became "session data stays in app-private storage."** The app never stores cookies itself: the WebView's `CookieManager` owns them in its own database under app-private storage, and `WebViewCookieJar` only reads and writes through it. `CookieManager` can't be pointed at encrypted storage, so encrypting would mean mirroring the session cookies into a second store (a second copy to steal, not a safer one) and adding `androidx.security:security-crypto`, which is off-stack and deprecated. Instead: exclude everything from backup and device-to-device transfer, and keep cookie details out of release logs.
    - **GitHub Releases and Obtainium dropped; installs stay on adb.** The repo is public, so any release would be a public APK. Weighed against build-from-source: a public APK makes my signing key every installer's trust anchor (a leaked key could push a malicious update that reads their AO3 session), turns a personal-use project into distribution (AO3 ToS and trademark exposure, support expectations, stale builds left downloadable), and runs into Google's developer-verification rules for sideloaded apps, which exempt adb installs **[verify current rules]**. A private releases repo with an Obtainium access token was considered and not needed: updates happen at the PC anyway. Revisit if updating away from the PC becomes a real want.

    2. **Cancel a running download (note 1)** *(done 2026-09-27)*: while a work downloads, the work page's bar shows **Cancel download** in place of the greyed-out button, and its Downloads row shows **Cancel**. Cancel removes the work from the queue. Built as an explicit per-download `DownloadCanceller` rather than coroutine cancellation: cancelling it cancels the OkHttp `Call` in flight, which closes the connection, so even a stalled read ends at once. The downloader returns a new `DownloadResult.Cancelled`. A cancel that lands after the new file has replaced the old one still returns Success and is saved, since with coroutine cancellation a late cancel would have left a file on disk with no library row, or skipped reconciling a WIP's reading position. A failure racing a cancel is treated as cancelled, not queued for retry. The Downloads screen's Remove goes through the same path (`DownloadQueueProcessor.cancel`), which also closes an older gap where removing a row just as the processor picked it up could still download it. Timeouts are unchanged (connect 20 s, read 60 s per gap between bytes): Cancel is the escape hatch. Tests: a real local socket whose EPUB response stalls mid-body is cancelled in about 0.2 s against a 60 s read timeout, leaving no `.part` file and the existing copy intact; plus cancel-before-start, cancel between the work page and the EPUB, and processor cases (running, late, racing a failure, not running, next work unaffected). Verified on the emulator with its network throttled to GSM: Cancel from the work page and from the Downloads screen each took effect within a second with the existing EPUB byte-identical, and a normal download afterwards completed. A re-download of an unchanged work came back byte-identical to the previous copy, small evidence toward the WIP **[verify]** in section 4, though AO3 may simply have served a cached file.
    3. **Error and offline states** *(done 2026-09-27)*: `network/NetworkMonitor.kt` keeps a process-wide `StateFlow<Boolean>` from `ConnectivityManager.registerDefaultNetworkCallback` (adds the `ACCESS_NETWORK_STATE` permission). It counts as offline only when the default network lacks internet capability, not when it's merely unvalidated: validation can stay false on networks that work, and treating those as offline would pause the queue indefinitely. The queue starts nothing while offline, and a `NETWORK` failure that happens once the connection has gone goes back to waiting without using an attempt (`countsAsAttempt`); any other failure, or one while still online, counts as before. If Android reports the loss a moment after the download fails, that one attempt still counts, which is accepted. Waiting works say "Waiting for a connection" on the work page and the Downloads screen, which also shows an offline banner. A page that fails to load while offline shows a "You're offline" panel with Open Library and Retry, and reloads by itself when the connection returns. The reader's failure screens (missing or damaged file, or a work no longer in the library) now have Back to library, plus Download again when the work is still in the library, which queues it and returns to the library. Verified on the emulator with airplane mode: a download tapped offline waited and completed about 10 s after reconnecting; the offline panel, its Open Library button and the automatic reload; the Downloads banner; and both reader failure screens. Download again was tested offline and its queue entry removed, so no request went out for a test work ID. The corrupt-file test row 990003 is no longer on the emulator, so the damaged-file screen was checked by temporarily overwriting 990001's EPUB and restoring it afterwards.

    5. **Version scheme and build-from-source docs** *(done 2026-09-27)*: `app/build.gradle.kts` has one `appVersion` (now **0.2.0**, for step 11), and `versionCode` is derived from it as major × 10000 + minor × 100 + patch (so 200); a malformed version, or a minor or patch of 100 or more, fails the build with a clear message. Android only refuses a *lower* `versionCode`, so reinstalling the same one works, which is why every install on `versionCode = 1` did. What the scheme buys is being able to tell which build is installed, and a guard against installing an older build over a newer one by mistake. ### Notes to revisit in Phase 3

Observations from hands-on testing of the Phase 1 build, to fold into steps 11 and 12 (or into step 7 if the download queue gets there first, since it already promises progress and failure display).

1. ~~**Cancel or abort a download in progress**~~ *(done in step 11, PR 2)* *(fits step 11, hardening; overlaps step 7)*. Right after tapping Download EPUB the button stays grey until the request times out, and there is no way out. Wanted: a Cancel control while a download runs, and a shorter, more honest failure path when the network stalls.
   - Today's client allows a 20 s connect and 60 s read timeout per request, and a download makes two requests, so a stall can take well over a minute to surface.
   - `EpubDownloader.download` is blocking. To cancel it, keep a handle on the in-flight OkHttp `Call` and call `cancel()` (or wrap the call so coroutine cancellation does it), and make sure a cancelled download leaves no `.part` file behind. It already cleans up on failure; add a test for cancellation.
   - Decide what timeouts feel right. AO3 can take a while to build an EPUB for a long work, so a short read timeout would cause false failures.
2. ~~**Make page loading obvious**~~ *(done in step 12, PR 6)* *(fits step 12, UI polish)*. The thin progress bar at the top of the browser is easy to miss. Wanted: a clearer indicator that a page is loading, for example a more prominent bar or spinner, and the refresh button reflecting the loading state (a stop control while loading).
3. ~~**Show download progress**~~ *(done in step 12, PR 6)* *(fits step 12, and step 7 for the queue)*. Wanted: visible progress while a work downloads instead of only a status line at the end.
   - Read `Content-Length` from the EPUB response for a determinate bar, and fall back to an indeterminate one when it is absent.
   - There may be a quiet gap before the first byte while AO3 builds the file, so show a "waiting for AO3" state distinct from "downloading", and distinguish the work-page load from the file transfer.
   - Report progress from the downloader through a callback so the queue (step 7) and the UI can share it.
4. ~~**Make deleting a work feel less abrupt**~~ *(done in step 12, PR 5)* *(fits step 12, UI polish)*. Today the card vanishes instantly and the list jumps. Wanted: visible feedback on removal, e.g. the card fading or sliding out while the rest of the list closes the gap smoothly (`LazyColumn` item animations), or a brief "Deleted" message.
5. ~~**"Not started" next to a "Last read" date**~~ *(done in step 12, PR 5)* *(fits step 12)*. A work opened but not read past the first page shows both. Possible fix: show "Opened, not started" in that case.
6. ~~**Library sort and filter reset on app restart**~~ *(done in step 11, PR 4)* *(small; fits step 11 or 12)*. They survive closing and reopening the library and activity recreation (`rememberSaveable`), but not a full process restart. Persisting them (e.g. SharedPreferences) is roughly ten lines.
7. ~~**Downloads screen shows "Work `<id>`" instead of a title**~~ *(done in step 12, PR 7)* *(fits step 12; from step 7)*. A title isn't known until the work page is fetched.

### Potential future improvements

Ideas worth keeping but not scheduled into any step. Pick one up only if a real need arises.

1. **Export and import the library** *(from step 11, 2026-09-27)*. Step 11 excludes all app data from backup and device-to-device transfer, so a phone migration doesn't carry the library over: you'd sign in again and re-download everything. A deliberate, user-triggered export would fix that without the leak the exclusion closes:

   - Never include cookies or anything else from the WebView; sign in again on the new device.
   - Import restores into an empty library (or merges, keeping the newer copy per work) and must handle archives from older schema versions.
   - Only matters if a phone migration is coming up. Until then, re-downloading is an acceptable cost.

   - *Opening animation:* a peeking pose would suit Pep peeking up from behind the book before the name appears, instead of the current rise.

## 6. Suggested architecture

- **Layers:** UI (Compose screens), data (Room, download storage), network (OkHttp with WebView cookie jar), and an isolated AO3 "adapter" layer holding all selectors, injected JS, and parsing.
- **Screens:** Browse (WebView), Library, Reader, and a Downloads/queue view (Phase 2).
- **Cookie jar:** a small OkHttp `CookieJar` that reads from Android's `CookieManager` for the AO3 domain.
- **Downloads:** a persisted queue (Room) processed by a single worker scoped to the app process — not WorkManager, not a foreground service. See the decision under "Open questions" below.

## 8. Open questions

- ~~Minimum Android version to target?~~ **Settled:** minSdk 26 (Android 8.0), target and compileSdk 35 (set in `app/build.gradle.kts`).
- ~~Where should downloaded EPUBs live?~~ **Settled in step 3:** app-private storage (`filesDir/works/<workId>.epub`), which is removed with the app and needs no storage permission. The README states that downloaded works stay private on the device.
- ~~WorkManager versus a simpler foreground service for the download queue?~~ **Decided 2026-09-23:** neither. A
  process-lifetime coroutine (the same pattern as `AppScope`, already used for saving reading position) processes
  a Room-backed queue. Queue *state* survives the app closing and resumes on reopen; downloads do not continue
  unattended once the process is fully killed (that tradeoff — option (a), "resumable," over option (b),
  "unattended" — was explicitly chosen as good enough for a personal app). WorkManager's deferred/constrained
  scheduling doesn't suit the queue's own tight retry/delay timing (`Retry-After`, sequential-with-a-pause), and a
  foreground service's persistent notification is an unwarranted UX cost for work that stays in-app. Revisit only
  if "keeps downloading while fully closed" becomes an actual want; the Room-backed state doesn't need to change
  either way.
- ~~Publish prebuilt APKs (GitHub Releases plus Obtainium) or build from source only?~~ **Decided 2026-09-27:** build from source only; I keep installing over adb. The reasoning is under step 11. Revisit only if over-the-air updates become a real want, and then with a private releases repo rather than public releases.
- ~~Should the library also store AO3 metadata (tags, summary, word count) at download time?~~ **Done in step 4:** read from the work page the download already fetches (no extra request); step 10's sorting and filtering are built on it.
